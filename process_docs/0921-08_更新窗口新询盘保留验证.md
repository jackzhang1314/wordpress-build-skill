## 实际失败与根因（全保留）

1. **双重编码根因**：检查脚本 `encode()` 辅助函数对传入值一律 `JSON.stringify`——传对象正确，但传「已是 JSON 的字符串」（payload）或裸 marker 字符串时会二次编码；PHP 侧解码后 marker 带字面引号，LIKE 查询落空，报 Submission missing。一处修复（字符串透传不 stringify）同时解决插入校验与查询。此前通过的 reset/preflight 未受影响，因为它们传的是数组/对象。
2. **清理静默误报**：修复前的失败运行里，清理验证用的 marker 同样损坏 → 查残留为 0 → 误报 cleanup=true，实际遗留 2 行。教训：清理验证必须用独立可靠键（数字 id），不得复用可能损坏的查询键。已按此加固。
3. 手动调试期间一次 `$wpdb->delete(['response LIKE'=>...])` 误用（delete 不支持 LIKE 条件）遗留 1 行，按 id 补删至零残留；该行是本轮调试产物，非业务数据。
