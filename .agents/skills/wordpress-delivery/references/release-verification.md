# 新站发布与后续迭代验收

当前公网目标仅 Hostinger Managed WordPress，按 [Hostinger 部署规范](hostinger.md) 区分首次发布、后续更新及远端验收。当前参考站的真实首次部署已验证，通用远程部署执行器尚未完成；本文的内容发布门禁不等于托管部署。

整站发布验证下列全链路；本方案建成站点的局部维护按影响范围验证，不能为小改动重复要求全站发布。project-record 的 release 回执不触发发布，也不替代本节门禁。

发布证据保存在任务目录，禁止把凭据、完整表单个人信息写入公开仓库。记录：

- 实际站点、核心/PHP/插件版本、HEAD 与未提交变更摘要；主题/插件文件哈希。
- 资源 ID/地址、模板所有权、内容更新前后指纹、字段映射及数据库迁移记录。
- 桌面与手机截图、浏览器错误、链接状态、编辑回显测试，以及各项 pass/fail/not-tested。
- 表单 UI、服务器记录、通知捕获、真实收件分别列状态。实验室拦截 wp_mail，不向演示邮箱外发。
- 代码与数据恢复快照、恢复步骤、实际演练结果。

询盘的四层证据、运行数据快照与隔离恢复，以及版本相关注意事项见 [验证与经验沉淀](verification.md)。

硬失败：PHP fatal、脚本模块解析失败、菜单不可用、主 CTA 404、必需表单缺失、表单失败却显示成功、数据编辑不回显、明显横向溢出、模板所有权冲突、发布版本与验收证据不一致。视觉评分不能抵消这些失败。

CLI build --publish 必须带 --evidence FILE。它校验连接/计划、精确页面集合、内容指纹与证据文件 SHA-256，并要求必要检查 pass。表单仅在任务确实无需表单时可写 not-applicable 并说明依据。此门禁不自动执行浏览器测试，不证明远端代码和本地文件天然一致；主题部署另做哈希核对。底层 buildSite 库调用方也必须执行 verifyPublication，不能绕过 CLI 声称门禁已通过。未实现的能力写 not-tested，不能写 pass。内容写入结果未知按日志恢复，不自动重发；文件同步成功只表示部署完成，重启与浏览器复验后才算验证完成。

目录引用面向可安装 Skill，不依赖仓库外 docs/14 等路径。可选设计 Skill 不在环境中时，使用本目录 design.md 的规则继续，不声称已读取不存在的能力。


## Evidence JSON

`identity` 从任务 task.json 取得；`planHash` 使用同一任务保存值。`pages` 必须覆盖计划中的所有实际页面；`fingerprint` 使用 read-page 返回的 releaseFingerprint。它忽略发布状态、时间和首页 URL 的合法变化，以允许中断后继续；正文、标题、模板、媒体变化会失效。

```json
{
  "identity": "<64位任务连接哈希>",
  "planHash": "<64位计划哈希>",
  "reviewedAt": "2026-09-19T22:00:00+08:00",
  "environment": {"wordpress":"实际版本","php":"实际版本","theme":"实际主题"},
  "checks": {
    "navigation":{"status":"pass","evidence":"菜单打开、关闭、Escape 与焦点返回的记录路径"},
    "primaryLinks":{"status":"pass","evidence":"全部主按钮实际目标和状态码记录路径"},
    "forms":{"status":"pass","evidence":"提交记录及本地通知捕获证据路径"},
    "editing":{"status":"pass","evidence":"字段图片正文编辑回显的记录路径"},
    "responsive":{"status":"pass","evidence":"桌面手机断点与溢出检查路径"},
    "visual":{"status":"pass","evidence":"当前版本截图与视觉评审记录路径"},
    "recovery":{"status":"pass","evidence":"快照和隔离恢复验证记录路径"}
  },
  "files":[{"path":"相对此证据文件的截图或源码路径","sha256":"<实际字节SHA-256>"}],
  "pages":[{"id":123,"fingerprint":"<read-page.releaseFingerprint>"}]
}
```

不预填通过状态：示例说明格式，只有完成对应验证后才可替换为真实证据。代码、截图和内容变化后重新审查。

## 本地验收与线上验收的划分

本地可完成原生 PHP/Web Server 部署、真实 MySQL 导出与隔离恢复、SMTP 测试邮箱收件、容器重建持久性和完整页面视觉评审。不要一概标为“只能生产验收”。具体方法见 verification 中“本地也可以验收生产技术链”。真实公网基础设施和真实邮件投递则绑定实际目标环境；本地验证结果保留其适用范围。


## 正式公开交付的搜索质量门槛

按 [search-quality.md](search-quality.md) 与 [seo.md](seo.md) 附逐页证据，至少覆盖首页、分类、详情、方案、About/联系、文章等实际页面类型。误留全站 noindex、重要内容仅为空壳、主要内链不可发现、错误 canonical、伪造产品/企业证据、无价值规模化页面等应修复后再标为正式交付；预览站按预览策略保留限制。

这些是总编排的人工/工具联合交付门槛。当前 `build --publish` 的 Evidence JSON 未增加 SEO/内容质量自动校验字段，不把这里的要求写成 CLI 已自动实现。可在现有任务证据目录保存补充报告并引用；缺失检查记录 not-tested，不伪造 pass，也不等待排名出现才完成本地技术验收。

## 增量更新：数据库模板覆盖门槛

更新区块主题前列出当前主题的 wp_template、wp_template_part 和全局样式覆盖，比较源码变更范围。后台保存的模板优先于对应主题文件：文件同步既不删除后台修改，也不保证新文件布局可见。不能自动删除全部覆盖来强制更新。

有冲突时保留后台版本，输出受影响模板及引用页面；根据本次授权明确选择保留、合并或重置。重置前备份对应对象，验证正文/ACF/图片/询盘均未丢失。模板文件更新测试与数据库迁移、远端传输、部署中新增询盘分别验收，不合并为一个笼统 pass。

参考仓库可运行 npm run test:starter:template-update：只在本地 reuse 实验站创建唯一测试产品、模板文件和数据库覆盖，验证文件被遮蔽、显式重置后新文件可见、产品字段和已有询盘保持及清理。它不连接生产，不代表模板部件、全局样式、媒体和完整增量部署都已验收。

参考仓库新增只读命令：`npm run starter:update-preflight -- templates/product-standard.html parts/header.html theme.json`。参数必须为实际变化的主题相对路径；检测当前主题已发布的模板/部件/全局样式数据库对象，只输出 ID、路径和哈希，命中对应路径返回退出码 2。空输入拒绝，不把“没传路径”当通过。当前适配器仅面向本地 reuse 实验站，不是 Hostinger 远端发布门禁；全局样式仅做 theme.json 级保守冲突提示，不做属性级合并。无冲突也不证明 CSS/动态块/插件变更不影响页面，仍需页面回归。

自动差异模式：`npm run starter:update-preflight -- --compare BEFORE_THEME AFTER_THEME`。对两个完整区块主题目录逐文件 SHA-256 比较，纳入新增/修改/删除，自动提取模板、部件和 theme.json 路径；拒绝符号链接及缺失主题标识文件。输出双方清单哈希和变更列表，CSS/PHP 等变化要求页面回归。输入目录必须分别对应实际部署基线和候选产物；该命令不自动证明基线就是线上版本。无差异不是发布授权，报告始终 releaseApproval=false。模板部件/全局样式的冲突扫描已用本地 WordPress 数据夹具验证，尚非两者的完整视觉合并测试。

基线快照与自动推导模式：`npm run starter:update-preflight -- --snapshot THEME_DIR OUT.json` 把候选或基线主题的逐文件 SHA-256 清单导出为 JSON，供增量流程留档和下次比较；`--baseline BASELINE.json CANDIDATE_THEME_DIR` 从已保存基线（`--snapshot` 生成的本地清单，或 `scripts/hostinger/theme-baseline.mjs` 的 Hostinger 只读报告）与候选主题目录自动生成变更路径，再按同一覆盖清单规则检查，无需手工罗列路径。Hostinger 报告的末尾换行归一化匹配按“仅差结尾 LF 视为未变”处理；基线 `unverified` 的二进制路径保持未验状态，既不进变更列表也不冒充已验证。基线哈希只反映采集时刻，不验证基线仍等于当前线上版本；基线模式下零冲突路径也会输出当前全部发布态覆盖供留档。无冲突仍不是发布授权。

Hostinger 远端只读预检：`npm run hostinger:remote-preflight [CANDIDATE_THEME_DIR]` 串起完整远端冲突检测——官方 CLI 只读采集远端主题基线（只读调用带三次退避重试）、同一派生逻辑生成变更路径、登录后经 REST（context=edit）盘点已发布的模板/部件/全局样式覆盖并求交集。全程零写入；凭据只从 `.wordpress-builder/hostinger/` 私有文件读取，报告不含凭据；旧基线报告自动按日期归档。REST 的 global-styles 列表在当前站不可用（报告 globalStylesViaRest=false），theme.json 数据库覆盖的远端检测仍是缺口；二进制文件与模板/部件/全局样式之外的数据库内容覆盖同样未覆盖。远端预检冲突仍是只读信号，处置（reset/restore）尚未接入远端。

远端处置已接入（REST 写通道）：`npm run hostinger:remote-resolve` 在远端执行与本地同语义的 reset/restore；备份落本地私有目录并校验后才删，删除经 force + previous 哈希核对 + GET 404 三重确认，restore 有 id 不存在前置与重建哈希核对。边界与授权要求见 hostinger.md「远端冲突处置」；cron/WP-CLI 通道、DB 层询盘核对、正式域名维护窗口流程仍未覆盖。

标题层级关卡：区块主题的模板/部件/模式在文档流中的标题级别须顺序合法（升幅不得超过一级；axe-core heading-order、Lighthouse 同标准）。参考仓库 `npm run test:starter:headings` 静态组装模板（解析 template-part 与 pattern 引用、剥离 PHP、按核心块默认级别补全：heading/post-title 2、query-title/site-title 1）后逐页判定。约定遵循 WordPress 官方主题惯例：列表类查询循环的 post-title 使用默认 h2 跟随页面 h1；单页正文标题显式 level 1；循环前有分区 h2 时条目可用 h3。发布包运行此命令且违规归零；渲染页层级在浏览器审计中复核。视觉样式一律挂在块 class 或显式字号上，不得依赖标题标签选择器，避免语义调整引起视觉回归。

冲突处置：预检命中冲突后用 `npm run starter:template-resolve` 显式处置，本地 reuse 适配器与预检同一环境。`keep PATH...` 为只读决策记录，输出命中的覆盖与哈希，不写入；`reset --backup OUT.json PATH...` 先把每条后台覆盖的完整内容写入备份 JSON（含 SHA-256），再删除覆盖让新文件生效，删除前重新校验内容哈希以拦截“预检到处置之间覆盖又被编辑”的并发写入，任一路径无覆盖则整批拒绝，不接受部分处置；`restore BACKUP.json` 从备份原样重建覆盖并校验主题与内容哈希，目标路径已有覆盖时拒绝以免产生歧义覆盖。`theme.json` 全局样式不做 reset/restore，仅保守提示。处置只保证数据库层语义，新主题文件必须在同一发布内交付；处置成功仍不是整站验收，页面回显按验收规范另行验证。

# 验证结果如何成为可复用做法

内容质量按 [search-quality.md](search-quality.md) 留下目的/事实/需求满足的评审证据；WordPress 专项与抓取检查按 [seo.md](seo.md)。评估员视角用于内部改进，不输出所谓 Google 官方质量分。

用于整站验收、真实问题修复和后续迭代。只检查本次受影响的链路；发布范围仍由 [release.md](release.md) 决定。

## Starter / 全新空站验收

“本地零媒体/零旧品牌”不等于远端也干净；seed 前后都要核对附件数、品牌 marker、路由清单和实际渲染。项目声明 `media.sources: []` 且媒体 map 为空时，远端媒体库应为空，残留 hero/product 附件就是回归。

全新站发布至少覆盖三类证据：
1. **路由与内容**：全量 `livePages` 加 CPT/taxonomy 代表页返回真实文档，逐页校验 H1、heading 层级、marker 和计数。
2. **视觉矩阵**：同一路由集合在 390/768/1440 截图，截图文件非空且抽样打开查看；Hostinger/LiteSpeed 缓存清空后再截。
3. **交互闭环**：表单必须先证明 DOM 中有真实 `<form>`，再做浏览器填写提交，最后比对数据库增量。短代码原文、空字符串或后台有表单但前台不渲染都不算通过。

失败部署必须验证 rollback 后的可用性；保留失败证据、根因和新增门禁。只修当前站而不把失败条件变成本地 check/verify 规则，不算沉淀完成。

## 询盘：分别取得四层证据

先确认实际表单插件的字段配置和当前版本 hook 签名，再记录：

1. 页面交互：从产品 CTA 进入、显示可读产品名、内部对象 ID 隐藏传递、必填错误与成功提示。
2. 服务端校验：构造不存在或不公开的产品 ID，确认未入库。隐藏字段同样可被客户端修改；不能只依赖前端控件。失败状态码由插件定义，不把某个 HTTP 码当成通用规范。
3. 数据库留存：提交前取得基线，提交后按返回的记录 ID 对照新增项、产品关联。重复运行按增量检查，不能假设数据库里永远只有一条记录。
4. 通知：本地捕获和真实收件分开记录。只有生产收件验证通过，才可宣称邮件送达。

验证不同失败/成功分支时重新打开表单，避免继承插件的提交中、冷却或错误状态。网络失败发生在提交之后时，先查询回执与数据库；不要因为测试脚本失败就再次提交。可重试明确只读的回读，次数需有上限。测试过程使用专用测试内容，公开证据不保存客户个人信息、凭据或数据库。

## 页面与后台编辑

REST 写入回显、浏览器后台保存、视觉检查是不同证据。ACF 字段在 REST 可写不证明运营者能找到并编辑它；至少在代表性页面实际打开后台字段、保存并读取前台，结束后恢复测试值。

主图验证依据附件 ID 对应的实际 WordPress 图片输出或资源 URL，不猜测必定存在 `wp-image-ID` 等 CSS 类。页面返回 200 不足以判断成功：同时核对最终 URL、文档壳、主标题、预期内容；不存在的路由应检查真实 404 状态，不能跟随到首页后算通过。

## 本地快照与隔离恢复

只有需要保留迭代状态或做恢复演练时执行。临时新建环境的 seed 是重建基线，不包含后续后台编辑、媒体或询盘，不能称为运行数据备份。

- 暂停内容编辑/上传等业务写入，在受控环境获得数据库一致性快照。不要直接复制正在写入的数据库文件。本项目的 SQLite 实验环境验证了 SQLite3 backup + integrity_check；生产 MySQL 使用对应数据库/主机的备份机制。
- 同时保存上传文件、主题、业务插件、实际第三方依赖和版本配置。记录文件哈希；私有快照可能包含用户、询盘、密钥材料，不能放进公开仓库。
- 恢复到独立目录、数据库和地址。只读原快照，先核验哈希，再用副本启动；不清空原站、不对恢复数据库重跑新站 seed。
- 比较稳定 ID、原生正文、业务字段、主图、上传文件及已有询盘；检查实际路由与实际运行版本。原快照哈希在恢复后仍应不变。
- SQLite/Playground 恢复通过只代表该环境；不自动满足正式主机的 MySQL、备份频率、异地保存、恢复时间等要求。

## 实验环境的启动判断

待 WordPress 运行证据产生、实际版本符合目标、REST 正常响应后，再更新“当前可用实例”指针。端口已占用、进程早退、临时 302、HTTP 200 的启动页面均不能算准备完成。CLI 日志中的版本目标不是实测版本。

Playground 3.1.52 的本地恢复实验中，Blueprint 未指定 preferredVersions 时曾出现实际 PHP 与 CLI 参数不一致；同时指定版本并读取 PHP_VERSION 核对。启动过程也可能改写 permalink 默认值，恢复后应核对快照配置。此为已观察到的版本行为，升级后重验，不据此对所有主机添加补丁。

## 每轮迭代怎样沉淀

探索阶段不以“修好本次问题”收尾。所有实际失败、阻塞、错误判断和用户纠正先记入同一阶段记录，同类合并；无通用结论也保留待验证项。对有复用价值的问题和成功做法，记录现象、触发条件、版本、原因/假设、修复、回归及边界；然后更新已有规范真源。稳定约束进项目 AGENTS，操作流程进对应 reference/playbook，能够机器判断的失败条件进入脚本或回归测试。交付时列出沉淀位置和未验证项，便于下一次同类任务直接使用。不要把本地或单一版本的成功扩展为所有主机都已通过。

- 已复现、已修复、已回归的做法：写入对应主题的 reference；重复且容易出错的步骤再提取成脚本，并实跑。
- 特定依赖版本的问题：写清版本、触发条件、证据和适用边界，不抬升为全局架构要求。
- 尚未验证的判断：留在项目待办，不写成 Skill 的既定事实。
- 向 `wp eval`/远端执行器传结构化数据时，base64/JSON 传输辅助函数必须让字符串透传、只编码对象，杜绝二次 stringify：曾因传输层双重编码使插入成功但按标记查询永远落空，且插入与查询用到同一损坏值。传输函数先用真实数据做一次往返校验再投入使用。
- 清理验证必须用独立可靠键（插入时返回的数字 id 等），不得复用可能与插入同一损坏路径的查询键：一次运行因 marker 损坏同时导致查不到和“残留=0”，误报清理成功。清理后残留以 id 精确计数为准。
- node:test 的 `assert.throws(fn, '字符串')` 会报 ERR_AMBIGUOUS_ARGUMENT，错误断言一律用正则匹配消息；CLI 用法错误在参数解析即失败，可在不启动任何环境的离线测试中断言退出码。

阶段记录保存本轮变更、失败尝试、最终证据及未覆盖项。已有阶段回执不静默覆盖；局部工具/文档迭代可以保留独立补充证据，不为其重跑无关的全站流程。

## 从源码运行到可安装交付

挂载源码成功与 WordPress 安装 ZIP 成功是两个检查点。交付前将主题和业务插件分别打包，在另一套空白实例使用 WordPress 安装流程激活；该实例不能把源码挂载到主题或业务插件安装目录。核对安装后文件的 SHA-256 与交付清单，再执行内容维护、询盘和恢复验证。依赖插件的版本与取得方式需单独记录。

代码包与运行备份分开：代码包只包含部署所需源码，运行快照留在私有目录；实验账户、邮件捕获、验收接口和 seed 不进入业务插件或主题。全流程复跑使用独立报告目录，遇到失败保留已完成步骤，不将部分通过记录为整站通过。内容写入后的读取失败先查状态，不自动重提询盘。

仓库 HONGDA 示例提供 `npm run hongda:e2e`，覆盖隔离新站 ZIP 安装、源码哈希、原生内容/字段维护、浏览器询盘和 SQLite 恢复。它不是通用主机安装器；需要本地依赖插件与 Playwright CLI。视觉认可、真实企业内容审核和生产验收分别记录，不能由功能测试推导。

## 本地也可以验收生产技术链

不要把“尚未验证”误写成“只能上线后验证”。将验证目标拆开：

- 部署与持久化：独立原生 PHP/Web Server 容器安装交付代码，连接真实 MySQL，重建 Web 容器后检查内容与上传文件仍在。记录实际镜像 ID、核心/PHP/数据库版本；不能用 SQLite 的成功代替。
- 邮件：使用 PHPMailer 的真实 SMTP 连接发送到本地 Mailpit 等测试邮箱，通过收件 API 验证收件人、内容与新增邮件数。这高于拦截 `pre_wp_mail` 的通知意图验证，但不等于 Gmail/Outlook 投递、域名认证或反垃圾信誉通过。
- MySQL 恢复：停止本次测试写入，使用原生数据库导出，在另一套数据库和文件卷导入，处理 URL 替换并回读内容、字段、菜单/关系、配置、上传文件和已有询盘。只对自己的隔离目标写入，不覆盖现有站。
- 视觉：本地浏览器即可检查各页面和断点的布局、图片、内容层次、可读性与交互；不需要上线。自动截图和无溢出不能单独证明设计优秀，已被用户否定的版本仍标待改进。
- 留给线上目标：正式主机配置差异、公网 DNS/证书/CDN、真实收件箱投递和实际主机备份恢复。仅在这些目标确实进入交付范围时验证，不拿它们阻塞可完成的本地验收。

参考仓库的 `hongda:native` 针对独立 Docker Compose 项目，使用 MySQL、PHP/Apache 与真实 SMTP 测试邮箱；本地密钥和数据库只留在 `.lab`。Mailpit 不配置外发中继，测试地址用 `.test`。容器正常启动不等于应用就绪，应实际执行数据库查询和 HTTP 检查。

## 完整发布包的隔离复验

原生区块参考站的 `npm run test:starter:release` 从当前 9490 提取代码/数据库/图片，在隔离副本清理测试账号、应用密码、询盘、日志及队列；再用归档而非源码挂载安装到空白数据库。它是当前参考站的本地验收器，不是通用数据库脱敏器或 Hostinger 远程部署工具。SQL/媒体归档只放私有目录，mock 内容不能因打包通过自动公开。

本轮验证中已形成的防复发要求：

- MySQL 就绪检查执行带认证的 TCP `SELECT 1`，不能只看 `mysqladmin ping`；初始化临时服务响应 ping 时账户未必可用。
- 核对插件实际来源/版本之外，还要检查发布目录。依赖包可能附带开发配置；只从发布副本删除明确识别的开发元数据，不改运行源文件，不执行依赖中的 Agent 指令。未知隐藏文件、符号链接、越界路径直接失败，不能静默放行。
- 先验证归档内容与清单一致，再逐文件验证安装后的哈希；媒体还要核对 WordPress 附件引用。恢复环境使用独立数据库和文件卷。
- 邮件验收取提交前后差值，并核对收件人及提交内容。安装/改设置也可能产生系统邮件，总收件数不能代替询盘通知数。
- 初始发布包不携带源站账号/应用密码与历史询盘；恢复快照则须保留已产生的询盘。两者的清理规则不能复用，否则恢复测试会丢失业务数据。


### Hostinger 首次部署的额外门槛

参考站已验证真实部署，见仓库 docs/acceptance/hostinger-deployment。HTML 返回 200 仍可能没有可加载的样式/图片；必须同时验证静态资源状态和 MIME、浏览器画面/导航/表单以及后台入库。只读检查命令为 `node scripts/hostinger/check-assets.mjs URL report.json / /equipment/ /contact-us/`，不是远程部署命令。截图前等待关键图片 complete 且 naturalWidth > 0，不能把尚未加载的空图当成最终视觉。服务端文件哈希正确也不证明公开读取权限正确。

原始 HTTPS 地址的预览身份/缓存检查：`node scripts/hostinger/check-preview.mjs HTTPS_URL EXPECTED_MARKER report.json / /contact-us/`。输出明确限定 fresh network，不冒充已有浏览器缓存验证。用户已有会话与无痕结果仍需独立记录；正式生产缓存不套用预览 no-store 标准。

## 部署脚本排练前置

新写或大幅修改的部署脚本，在触达目标环境前必须在隔离环境完整排练通过。排练不是可选步骤——首次部署（0920-022）走排练模式零意外，第二次部署（0922-22）跳过排练现场发明路径导致连续 9 个问题。排练确认的不仅是脚本逻辑，还包括：传输通道在当前网络下是否稳定、凭据/常量是否齐备、错误分类是否覆盖当前环境的新形态。

部署脚本的三个易漏项：
- Application Password 创建必须内嵌在 deploy.php 中（部署=零接触，完成后立刻有凭据），不得作为后续步骤单独执行——SQL 导入会覆盖用户表，时序颠倒会导致凭据失效。
- WP-CLI eval 中的 PHP 变量通过 shell 传递时会被吃掉（$变为空），改用 eval-file 或写入临时 PHP 文件执行。
- 转义层数：嵌入 base64/JSON 的内容在多通道传输时反斜杠会翻倍，写入后必须用正则或字节检查确认实际内容。
- 错误通道：CLI/API 错误信息可能在 stdout 而非 stderr——错误分类只查 stderr 会漏掉关键信息。
- no-op 语义：0 变更是收敛成功而非断言失败，不得当作异常退出。

## CMS 验收闭环

先盘点每种内容类型、分类、模板和媒体，保存私有基线。逐条内容的克隆草稿写入/回读/渲染与实际后台 UI 验收分别记账；代表 UI 覆盖正文、ACF、媒体上传/替换/替代文本、模板选择、分类布局、导航、SEO、发布/回收站/恢复及询盘管理。不能仅以 REST 200 声称后台可用。测试 ID 建立归属清单，清理后比较原有业务字段，保留初始失败和修复后证据。

保存提示可能缺失，优先核对持久化回读和前台输出；不要 force click 绕过编辑器遮罩。ACF 的 revision 预览与 REST 已保存字段可能不同，分别验证真实 UI 预览与保存态，不能拼 URL 后将空字段直接判成数据丢失。具体版本现象留项目记录。
