# 页边：外贸专业插件场景与 Skills 调研

调研日期：2026-09-05。对象：中国出口企业、外贸 SOHO 与服务商中的业务员、阿里国际站运营、独立站运营和广告投手。基线：当前页边 v0.3.9。

这是公开资料和当前源码支撑的产品建议，不是用户访谈结论、已实现功能清单或效果承诺。用户已确认先前所说的“ICU”指 SEO；本报告将独立站自然搜索优化作为重点，与 Google、Meta、LinkedIn 付费广告分别讨论。

## 1. 产品判断

建议定位为：**在客户正在工作的网页上，理解公司和产品，帮助外贸团队完成获客、询盘处理与网站优化的工作助手。**

最有价值的组合是“公司产品资料 + 当前网页证据 + 专业判断 + 可直接采用的交付物”。例如，在询盘页上提取客户需求，用自己的产品资料判断能否满足，补齐追问，写成可编辑的回复，并把该客户保存下来。

跨岗位可以共用企业资料、产品事实、客户档案、来源证据与任务记录；每个页面展示该场景的少数操作。首发建议面向制造业 B2B 中兼顾获客与询盘的小团队，先完成询盘、背调、落地页诊断三条流程。复杂广告账户管理与完整 CRM 放到数据接入阶段。

这个排序依据当前插件复用程度、预期任务频率、交付结果是否容易核验、平台适配成本与误操作影响，属于待验证的优先级假设。阿里运营、独立站运营、投手和业务员不能被视作完全相同的用户。

## 2. 调研中影响定位的证据

### 2.1 平台原生 AI 已覆盖大量基础功能

Alibaba.com 印尼卖家官方页面介绍的 Smart Assistant Agent 已包含产品发布、询盘回复、RFQ 机会开发、店铺诊断和运营周报等流程。这证明这些任务有明确的平台需求，同时意味着通用标题改写、询盘润色等功能面临直接竞争。页面属于区域产品介绍，不能据此断言中国所有卖家账号已拥有完全相同入口，也不能把营销材料中的提效说法当作独立验证结果。[官方产品介绍](https://seller.alibaba.com/id/smart-assistant-agent)

由此推断，页边更应积累跨平台的企业资料和客户上下文，并把网页诊断变成可执行的批注任务。用户在阿里看到的询盘、在客户官网查到的资料、自己的产品参数和邮件回复应能连续使用。

### 2.2 销售 Skills 已有成熟的工作拆分方式

Anthropic 的 Sales 插件将客户研究、触达草稿、竞争情报、会议准备等拆成独立技能，并区分仅靠网页搜索/用户输入与连接 CRM、邮箱后的能力。可借鉴其工作拆分和交付结构；它的连接器不会随着 SKILL.md 导入页边而自动获得。[Sales README](https://github.com/anthropics/knowledge-work-plugins/blob/main/sales/README.md)

### 2.3 外贸广告需要经营结果，而不仅是表面转化

Google 官方区分 Qualified lead 与 Converted lead：线索是否合格、是否推进到企业定义的成交或转化阶段，需要线下系统或 CRM 的数据。因此页边应区分表单提交、有效询盘、报价、样品和订单，缺少真实来源时保留未知。[Google 官方说明](https://support.google.com/google-ads/answer/10029210?hl=en)

### 2.4 SEO 和投放复盘不能只读当前可见页面

Search Console API 可以按查询、页面等维度返回搜索表现；正式 SEO 机会判断应结合有日期范围的数据，而非只根据页面措辞猜搜索量或排名。[Search Analytics](https://developers.google.com/webmaster-tools/v1/searchanalytics/query)

广告页面可能有分页、虚拟滚动、隐藏列和不同统计口径。首版建议支持报表导入，标明账户、日期、币种、过滤条件与覆盖范围；账户直连放在后续。Google 官方已有账户诊断 Skill，但明确依赖 Google Ads MCP 的账户发现和查询工具。[官方诊断 Skill](https://github.com/google/skills/blob/main/skills/ads/google-ads-api-account-diagnostics/SKILL.md)

## 5. 最值得先做的三个完整功能

### 5.1 询盘工作台：从读懂询盘到可发送的草稿

入口：用户在询盘/邮件页面点击“处理这条询盘”，或选中一段消息。首版选择一个真实高频页面完成适配，再增加平台。

步骤：识别客户与需求 → 匹配企业产品 → 列出影响报价的缺项 → 给中文分析和客户语言草稿 → 用户编辑 → 填入当前回复框。发送应是独立动作；草稿生成不能自动承诺未经确认的价格、产能、证书、交期或账期。

结果卡包含：客户要什么、哪些产品匹配、还需问什么、建议下一步、回复草稿、引用资料及客户档案。没有产品资料时先输出需求摘要和追问，明确不生成承诺。

示例（虚构场景，仅说明产品行为）：客户询问某阀门 500 件，插件发现没有口径、压力和介质信息，先提取这三个缺项，并根据企业术语表写一封简短追问邮件；不会直接猜型号和报价。

它的持续价值来自企业资料复用和客户上下文，质量指标应看用户改了多少、是否漏掉关键规格、是否出现错误承诺，以及完成一条询盘的实际时间。

### 5.2 客户背调卡：帮助判断是否值得跟进

入口：客户官网、公司名称、邮箱域名或询盘中的公司信息。

首版基于当前网站给出：企业名称与域名是否对应、经营哪些产品、可能的客户类型、与自己产品的匹配依据、已知事实、未知项及可用于交流的切入点。更完整的背调再通过公开搜索或用户加入的网页补证。

“客户匹配度”和“购买意图”必须分开：销售某类产品只说明可能相关，不等于正在采购。公开网页未找到资料应显示未核实，不能由此直接判断客户是骗子，也不输出凭空的采购额或信用分。

每条关键判断可以回到原网页；结果可保存到客户清单，并转交询盘/开发信流程。只收集公开出现的联系方式；个人邮箱验证、海关交易记录等需专门数据来源，不能由模型补造。

### 5.3 落地页诊断：让建议落到具体元素

入口：打开自己的页面，点击“检查这页能否带来询盘”。用户可以附加广告词、目标国家与产品。

围绕采购决策检查：首屏是否说明供应什么及适用客户、规格是否够采购判断、制造/品控证据是否充分、MOQ/定制/交期是否清晰、手机端联系入口和表单是否可用，以及广告承诺是否能在页面找到依据。

输出不要只有泛泛评分。将每条发现绑定到标题、参数表、认证区或表单：原文/原位置 → 问题依据 → 改稿 → 验收条件。用户可以接受为批注、编辑、分派或导出给建站人员。

当前插件已经有定位、截图、样式预览和导出，是最有差异化的基础。但 Agent 目前只有 readAnnotations，没有创建诊断批注的工具；这一步需要正式开发。源码修改和发布仍需要 CMS 或代码工作流接入，浏览器临时样式不代表网站已上线修改。

### 将 SEO 纳入同一个页面工作台

页面工作台同时提供“搜索表现”和“询盘转化”两个检查角度，首版先做有页面证据的部分。

1. **页面级 SEO 检查**：读取 title、description、H1/标题层级、canonical、robots 指令、内链和图片 alt，结合目标查询给出原值与建议值。源码和渲染后 DOM 的差异应能标明；当前 DOM 工具需补充这些字段。浏览器可打开页面不代表 Google 已抓取或收录。
2. **B2B 搜索意图检查**：区分产品采购、供应商选择、技术选型、应用方案与资料学习；判断应由产品页、分类页、应用页或文章承接。没有关键词工具数据时只给语义判断，不生成伪造的搜索量和竞争度。
3. **内容补充建议**：根据真实产品资料补规格表、选型条件、应用、定制范围和常见采购问题；每个新增事实可追溯到企业确认的资料。Google 对生成内容强调准确、质量与相关性，因此产品重点应是帮助补齐真实采购信息。[Google 内容指导](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)
4. **GSC 机会清单**：导入或连接数据后，按查询、页面、国家、设备和日期发现有曝光低点击、查询与页面不匹配、值得补内容的页面。结合搜索意图与转化目标排序，不把所有低 CTR 都归因于标题。
5. **多语言与修改复查**：后续检查 hreflang、canonical、翻译中的参数/单位一致性；记录修改前后值和发布日期，再按相同口径观察。排名变化同时受季节、竞争和平台变化影响，不自动认定由某次改稿造成。

标题建议使用描述性、简洁且贴合页面内容的表达，不把固定字符数视为 Google 的硬性排名标准。[Google 标题指导](https://developers.google.com/search/docs/appearance/title-link)

这让 SEO 人员获得的交付物是“哪页优先改、改哪个字段、补哪些信息、如何交给编辑/开发、之后看哪项指标”。它与现有网页批注功能可以共享大部分交互。

## 6. 广告专业功能应怎样做

首个广告入口建议是“分析这份搜索词报表”，而非让用户连接整个账户后立即自动改预算。

流程：读取 CSV → 识别日期、币种、账户和字段 → 按企业产品判断搜索意图 → 显示分类理由与覆盖范围 → 生成候选操作表 → 用户筛选导出。应提供品牌词保护、否词影响预览，以及“保留观察”状态。

例如，词里带 wholesale、supplier、manufacturer 不能自动等同于好词，出现 repair、parts 也不能自动否定；对卖配件或维修设备的企业，它们可能十分相关。判断必须依赖产品和业务边界。

后续接 Google Ads、GA4 和 CRM 时，分别维护平台转化、表单提交、去重线索、有效询盘、订单等口径。只有取得真实且允许使用的关联数据，才展示每有效询盘成本、成交成本或收入回报；没有数据时显示不可计算。

Meta/LinkedIn 先复用同一个数据输入和比较框架，再增加素材、受众和表单维度。公开广告库可用来研究表达、卖点和落地页；不能仅凭广告在投或投放持续时间断言它盈利。Google 官方支持按广告主/网站、地区和日期检索广告，是竞品素材研究的可用入口。[广告透明度说明](https://support.google.com/My-Ad-Center-Help/answer/12155361?hl=en)

## 7. 让用户愿意每天使用的产品基础

### 企业资料只维护一份

至少保存：企业介绍、产品参数/型号、MOQ、定制能力、经确认的交期与报价规则、证书/案例证据、目标市场、目标客户、术语表、禁止承诺事项、资料更新时间。优先让用户导入现有产品表或选择官网资料，确认后复用。不要要求先完成冗长问卷才能体验首个任务。

企业事实、客户事实、任务指令应分开保存。内部成本与对外价格分开授权，避免草稿把不应外发的字段带出去。多公司/多店铺用户必须明确当前档案。

### 页面驱动入口

侧栏根据当前工作显示 3–4 个动作，例如“处理询盘、客户背调、检查产品、检查落地页”。用户仍能自由聊天，技能库作为高级管理入口。不要要求外贸用户学习 SKILL.md、MCP、GAQL 等术语。

识别到站点不等于已有稳定适配。每个适配器要显示读取范围，处理分页、选中会话、富文本框和表单字段；拿不到数据时允许粘贴或导入文件。

### 交付物可编辑、可采用、可追溯

回复卡提供复制和填入草稿；诊断卡提供创建批注和导出；客户卡提供保存、去重和跟进；搜索词卡提供分类修改和导出。所有成果离开聊天也能继续使用。

“采用建议”记录实际采用的版本；之后问用户是否有回复、是否变成有效询盘，逐步形成企业自己的案例。未获用户确认，不把某次改稿自动升格成长期规则。

## 8. 技术适配路线

| 当前基础 | 下一步增量 | 目的 |
|---|---|---|
| 原生侧栏、对话和任务组 | 页面场景识别、角色快捷入口 | 打开网页就能开始相关工作 |
| 现有 SkillRuntime | 外贸技能包装、引用重写、依赖能力标识 | 区分可运行、需资料、需接口、仅方法参考 |
| IndexedDB 对话记录 | 企业/产品/客户持久档案 | 跨任务复用真实业务事实 |
| DOM 快照、批注选区 | 元数据/表格提取、Agent 创建批注 | 把检查结果绑定网页证据 |
| 表格和摘要卡片 | 询盘卡、客户卡、页面诊断卡、搜索词卡 | 用户直接编辑与采用结果 |
| 当前文件仅用于技能导入 | 通用 CSV 导入、字段映射、确定性计算 | 先服务运营报表与广告复盘 |
| 当前截图只展示给用户 | 可选视觉输入、支持对应模型与费用提示 | 理解产品图、页面视觉和广告素材 |
| 当前网页权限机制 | 平台适配器与按动作授权 | 稳定写入草稿并明确最终提交 |
| 当前无平台数据直连 | OAuth 与服务端/API 连接器 | 广告、GSC、CRM 等全量数据 |
| 当前无持续后台业务调度 | 后续任务提醒/定时执行服务 | 浏览器关闭后的跟进或监测 |

### 当前已确认的 Skill 导入问题

- 当前正文上限 16,000 字符，每包最多 64 文件/2 MB，一包只允许一个 SKILL.md；多个技能的仓库不能整库 ZIP 后直接导入。
- Corey ads、GoMarble Google Ads 与 Google MCP setup 的当前正文超过上限；应抽取核心流程，把参考资料拆分按需读取，而非单纯无限放大上下文。
- 外层目录引用必须重写为包内路径；多个 Skill 的交叉调用不能假设宿主自动实现。
- tradehot 的 metadata 中包含数组和对象，当前导入器要求 metadata 为字符串字典，原包会在元数据校验失败。应生成兼容版或明确扩展产品契约。
- Python/终端脚本只能作为文本保存和读取；需要浏览器重写、服务端工具或宿主能力后才能执行。
- 当前可同时激活最多 4 个技能、总正文 24,000 字符；把一个用户任务设计为有限技能组合，不把整座技能库全塞进模型上下文。

建议每个内置技能声明：所需企业资料、页面/数据来源、所需工具、输出结构、禁止猜测的字段、参考资料更新时间、验证样例和适配版本。原仓库的下载/安装指令只是开发者参考，不应出现在普通用户流程中。

## 9. 实施顺序和验证

### 阶段 A：验证核心工作价值

开发企业简档与产品事实、询盘需求卡/草稿、当前网站背调卡、落地页诊断批注，并在页面工作台纳入页面级 SEO 与搜索意图检查。首发先选择一个具体出口品类、一个常用询盘页面；底层数据结构保留扩展空间。

先用真实用户授权的历史任务进行对照评估。建议邀请 8–12 人覆盖业务员、阿里运营、独立站运营与投手；这只是访谈计划，不是已经完成的样本。观察他们完成任务，而不是只问“是否喜欢这个功能”。

### 阶段 B：增加反复使用的理由

增加客户清单与去重、产品档案导入、多语种术语、CSV 报表、搜索词分类和运营周报。把用户已采用的改动与下一步任务关联起来。

### 阶段 C：接通业务结果

根据前两阶段的实际高频需求接 GSC、Google Ads、CRM/邮箱。优先做只读数据与可靠归因，再设计明确操作范围、回读确认和失败恢复的写入流程。需要账号审批和接口权限的阶段不提前承诺上线日期。

### 阶段 D：扩充平台与行业

扩充阿里 RFQ/产品编辑器适配、Meta/LinkedIn 分析、报价文件、团队协作和市场简报。每项按使用需求单独验收。

### 建议观察的指标

| 功能 | 最先看什么 | 不能用什么冒充成果 |
|---|---|---|
| 询盘助手 | 完成时间、关键字段遗漏、草稿修改程度、错误承诺 | 生成邮件数量 |
| 背调 | 事实准确度、来源可追溯率、用户是否采纳下一步 | 凭空的客户信用分 |
| 落地页诊断 | 建议被接受/修复数量、问题定位准确度 | 单次 AI 健康分 |
| 广告复盘 | 统计可对账、分类采纳、业务反馈闭环 | 没有 CRM 数据的 ROAS/有效询盘成本 |
| 整体产品 | 每周完成且被采用的真实任务数、次周主动复用 | 只看打开侧栏或聊天次数 |

首次验证不必预设“提升多少询盘”的宣传数字。先证明能可靠完成任务、节省可测量的操作时间，再跟踪业务结果；外贸成交周期较长，不能从几天试用推断收入增长。
