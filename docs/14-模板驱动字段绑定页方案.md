# 模板驱动字段绑定页方案：customTemplates + ACF + Block Bindings + CPT

- 记录时间：2026-09-19 06:20 Asia/Shanghai
- 触发原因：用户确认 ACF 为必装基座，不再做「ACF 与原生 meta 二选一」；需要把「自定义页面模板 + 自定义内容类型 + 字段绑定」补充进现有 Codex + WordPress 原生区块建站方案。
- 决策结论：正式方案以 **Block Theme + customTemplates + CPT + ACF field group + ACF Block Bindings + REST** 为标准组合。原生 `core/post-meta` 只作为无插件降级知识保留，不作为本方案默认实现。

## 1. 架构定位

这套补充方案不是替换前面的「原生区块 + Block Theme + CPT/ACF + REST」架构，而是把它的数据驱动页面部分收敛成一个更稳的标准做法：

| 层 | 载体 | 负责内容 |
| --- | --- | --- |
| 结构层 | Block Theme、`templates/*.html`、`theme.json customTemplates` | 定义产品页、案例页、行业页等页面骨架，保证前台与编辑器使用同一结构。 |
| 数据层 | CPT、ACF field group、媒体、分类法 | 承载型号、参数、图片、卖点、询盘 CTA、案例结果等业务数据。 |
| 表现层 | Design token、block pattern、style.css、模板 CSS | 控制排版、栅格、颜色、组件状态和响应式，避免模板变成裸 HTML。 |
| 绑定层 | ACF `acf/field` source、Block Bindings API | 把标题、段落、图片 URL、按钮文本/链接等绑定到 ACF 字段。 |
| 编辑层 | WordPress 管理后台、ACF 字段表单、template lock | 让运营者改字段和媒体，而不是破坏页面结构。 |
| 自动化层 | Codex 工具、WP REST API、视觉 QA | 批量生成页面、填充字段、替换模板、验证前台效果和可编辑性。 |

核心价值在于三层解耦：**设计由模板和 pattern 负责，数据由 CPT/ACF 负责，内容运营由 WordPress 后台负责**。AI 负责生成结构与字段 schema，不把最终站点变成一次性静态 HTML。

## 2. 机制拆解

### 2.1 customTemplates

Block Theme 可以在 `theme.json` 的 `customTemplates` 中注册模板：

```json
{
  "customTemplates": [
    {
      "name": "product-dynamic",
      "title": "Product detail: data binding",
      "postTypes": ["oct_product"]
    }
  ]
}
```

对应文件放在 `templates/product-dynamic.html`。`postTypes` 让模板只出现在指定 CPT 的可选模板中，避免产品模板污染普通页面。

要点：

1. `single-{post-type}.html` 是模板层级默认模板，适合 CPT 的通用默认页。
2. `customTemplates` 是显式可选模板，适合同类型对象有不同版式的场景，例如「标准产品页」「重型设备页」「附件页」。
3. 模板文件属于主题版本控制，不应把正式结构保存进 WordPress 数据库的 `wp_template` 覆盖记录。
4. 后台模板编辑器一旦保存，会产生数据库模板并优先于主题文件。AI 管线默认只写文件模板，不写数据库模板。

### 2.2 CPT 与 ACF field group

CPT 定义业务对象，例如 `oct_product`、`oct_case`、`oct_industry`；ACF 定义该对象的业务字段。字段组应通过代码注册，而不是只存在后台数据库里：

```php
acf_add_local_field_group([
  'key' => 'group_octopus_oct_product',
  'title' => 'Trade details',
  'show_in_rest' => 1,
  'location' => [[[
    'param' => 'post_type',
    'operator' => '==',
    'value' => 'oct_product',
  ]]],
  'fields' => [
    [
      'key' => 'field_oct_model',
      'name' => 'oct_model',
      'label' => 'Model',
      'type' => 'text',
      'allow_in_bindings' => true,
    ],
  ],
]);
```

ACF 必须启用 `show_in_rest`，否则 Codex/REST 管线读取和写入会缺少 `acf` 对象。字段必须设置 `allow_in_bindings: true`，否则不会进入 Block Bindings 输出。

### 2.3 ACF Block Bindings

ACF 6.8+ 文档给出的绑定源是 `acf/field`，可用属性包括：

| 区块 | 可绑定属性 |
| --- | --- |
| `core/heading` | `content` |
| `core/paragraph` | `content` |
| `core/image` | `url`、`alt`、`title` |
| `core/button` | `text`、`url` |

区块标记形如：

```html
<!-- wp:heading {"metadata":{"bindings":{"content":{"source":"acf/field","args":{"key":"oct_model"}}}}} -->
<h2 class="wp-block-heading"></h2>
<!-- /wp:heading -->
```

图片绑定：

```html
<!-- wp:image {"metadata":{"bindings":{"url":{"source":"acf/field","args":{"key":"oct_gallery_image"}}}}} -->
<figure class="wp-block-image"><img src="" alt=""/></figure>
<!-- /wp:image -->
```

按钮绑定：

```html
<!-- wp:button {"metadata":{"bindings":{"text":{"source":"acf/field","args":{"key":"oct_cta_text"}},"url":{"source":"acf/field","args":{"key":"oct_cta_url"}}}}} -->
<div class="wp-block-button"><a class="wp-block-button__link"></a></div>
<!-- /wp:button -->
```

官方 Block Bindings 集成文档还要求 WordPress 6.7+、ACF 6.8.1+ 和 datastore 开启。本仓库当前本地验证环境为 WordPress 7.1、ACF 6.8.9；实测插件源码显示免费版默认注册了 `acf/field`，因此前台服务端绑定可用。若项目使用更老版本或未来版本行为变化，必须在安装后探测 `register_block_bindings_source('acf/field', ...)` 是否存在，并在工具链中直接失败，而不是静默降级。

## 3. ACF 基座决策

用户已确认：ACF 是必装插件，不是推荐插件。理由如下。

1. **后台体验稳定**：ACF 提供字段分组、字段类型、必填校验、展示位置、媒体选择、说明文案等，运营者不需要理解区块 JSON。
2. **内容模型可读**：型号、材料、MOQ、交期、参数、卖点、CTA 都是显式字段，避免把业务数据埋进长文章正文。
3. **REST 输出一致**：开启 `show_in_rest` 后，REST 响应包含 `acf` 对象，Codex 可以按 schema 读取和写入。
4. **绑定语义清晰**：`acf/field` 直接面向字段，模板不需要自行定义自定义绑定源。
5. **扩展空间大**：后续 Options Page、Repeater、Gallery、Relationship、条件字段等可继续挂在同一套 ACF 体系上。

因此方案标准是：

1. 新项目必须安装并激活 ACF。
2. 内容建模阶段必须输出 ACF field group 代码或可导入 JSON，不把字段组只留在测试站数据库。
3. 能用 ACF 表达的业务数据直接用 ACF；正文长叙述仍放 `post_content`，不要全部字段化。
4. 不维护「ACF 字段 + 原生 meta 表单」两套编辑入口；旧数据可兼容读取，但新实现不得继续增加第二编辑入口。
5. 工具链发现 ACF 缺失时停止内容模型步骤，并提示安装/激活 ACF。

## 4. 三种页面生成模式

### A 模式：自由组合页

适用：首页、品牌故事、解决方案页、落地页。

- 页面主体来自 `post_content`。
- 结构由 block pattern 和受控区块组合生成。
- 页面级字段少量保留，例如 hero 标题、副标题、CTA。
- 编辑自由度较高，但需要 pattern 和视觉 QA 约束。

### B 模式：模板绑定页

适用：产品详情、案例详情、服务详情、团队成员详情。

- `customTemplates` 或 `single-{post-type}.html` 定义版式。
- ACF 字段绑定到 heading、paragraph、image、button。
- `post_content` 保留长叙述和验证性内容。
- 同一模板可复用到几十、几百条 CPT 数据。

### C 模式：查询归档页

适用：产品列表、案例列表、分类页、标签页、搜索页。

- 使用 `archive-{post-type}.html`、`taxonomy-{taxonomy}.html`。
- `core/query` + `core/post-template` 输出列表卡片。
- 列表卡片用 pattern 控制视觉；单卡字段来自标题、摘要、特色图、分类和少量 ACF 字段。

| 模式 | 结构来源 | 数据主体 | 复用性 | 编辑风险 | 推荐用途 |
| --- | --- | --- | --- | --- | --- |
| A | Pattern 组合 | 页面正文 | 中 | 中 | 首页、营销页 |
| B | customTemplates | CPT + ACF | 高 | 低 | 产品/案例详情 |
| C | 归档模板 | Query Loop | 很高 | 低 | 列表和归档 |

### D 模式：PHP 混合自由模板（Block Theme 内的原生自由 HTML）

用户确认的补充决策：视觉复杂、需要像素级设计的复用型页面（产品详情、产品分类页）优先使用自定义页面模板的自由 HTML 渲染，不把全部版式硬塞进区块 JSON。

Block Theme 的原生实现路径不是把 PHP 写进 `templates/*.html`，而是利用 WordPress 模板层级的 PHP fallback：

1. `templates/index.html` 必须保留，WordPress 才把主题识别为 Block Theme。
2. 在主题根目录放 PHP 模板（如 `single-oct_product.php`、`taxonomy-oct_product_category.php`），`get_query_template()` 会先按层级 `locate_template()` 找 PHP，再走 `locate_block_template()` 找区块模板。
3. **优先级规则（需实测确认）**：区块模板优先于 PHP 模板。若 `templates/single-oct_product.html` 与根目录 `single-oct_product.php` 同时存在，前台命中 `.html`。要让自由 HTML 生效，必须删除同名区块模板。
4. PHP 模板内使用 `get_header()` 不适用于 Block Theme 的 `parts/`；应改用 `block_template_part( 'header' )` / `block_template_part( 'footer' )` 引入区块部件，并手动输出 `wp_head()` 与 `wp_footer()`。
5. 自由 HTML 部分用 `get_field()` 读取 ACF 字段（包括 CPT 与 taxonomy 字段），用主题级 CSS（复用 `theme.json` token）渲染任意布局，不受区块结构限制。

数据层不变：ACF 仍是唯一字段真源，REST 仍可读写 `acf` 对象；自由模板只是把「渲染层」从区块引擎换成主题 PHP，内容层依然可被后台表单和 Codex REST 管道编辑。

| 模式 | 渲染层 | 设计自由度 | FSE 可视编辑 | 推荐用途 |
| --- | --- | --- | --- | --- |
| B | `.html` 区块 + Block Bindings | 中（受区块约束） | 是 | 常规详情页、后台需改版的页面 |
| D | 根目录 PHP + `get_field()` 自由 HTML | 高（任意 HTML/CSS） | 否（模板由代码管理） | 像素级产品详情、分类页、专题页 |

落地规则：

1. 产品详情默认 D 模式：`single-oct_product.php`，删除 `templates/single-oct_product.html` 防止区块模板抢优先级。
2. 产品分类默认 D 模式：`taxonomy-oct_product_category.php`，删除通用 `templates/taxonomy.html`；`oct_case_industry` 退回 `archive.php`/`index.html` 兜底（后续可按需补 PHP）。
3. 同时保留 `templates/product-dynamic.html`（区块绑定版）并注册进 `customTemplates`，需要后台逐篇切换的页面仍可选 B 模式。
4. PHP 模板的视觉必须复用同一套 design token（`style.css` 的 `--tl-*` 变量），禁止模板内另起一套样式体系。

## 5. Codex 管线接入

8 阶段管线映射如下。

1. **Brief**：确认对象类型、字段边界、语言市场、询盘路径。
2. **Sitemap**：为每类页面标注生成模式 A/B/C。产品详情、案例详情默认 B；产品列表、案例列表默认 C。
3. **内容模型**：输出 CPT、taxonomies、ACF field group、字段 REST 名、必填规则和绑定属性。ACF 必装检查放在本阶段。
4. **设计系统**：先定 token 和组件 pattern，再写模板，避免每个模板自己发明样式。
5. **页面生成**：
   - A 模式走页面 block plan。
   - B 模式写 `templates/*.html` 和字段绑定。
   - C 模式写归档模板和 Query Loop 卡片。
   - D 模式写根目录 PHP 自由模板（`get_field()` + 主题级 CSS），并删除同层级区块模板避免优先级冲突。
6. **视觉 QA**：模板只需首轮全量验证；每个新增 CPT 对象抽查渲染、空字段、移动端和对比度。
7. **修订**：结构问题改主题模板；内容问题改 CPT/ACF 数据；不要在单篇内容里硬改结构。
8. **发布**：发布 CPT 与页面，配置导航，检查 REST 数据、前台绑定、后台可编辑性。

当前演示采用 `oct_product` CPT，ACF 字段组通过代码注册。

模板结构：

1. 顶部：header template part。

3. 规格带：四项参数按 2×2 移动端单列展示。

5. 卖点：三个 ACF 卖点组成工业风卡片。
6. 询盘 CTA：按钮文本与链接绑定 ACF。
7. 底部：footer template part。

当前工具链已有模板读取与模板修改命令；字段绑定还需要把「字段 schema → 绑定模板」的生成规则纳入标准 plan/apply 输出，并在申请单中记录每个绑定字段。

## 7. 验收清单

1. ACF 插件处于激活状态，field group 的 `show_in_rest` 为 true。
2. REST GET `/{post_type}/{id}` 返回 `acf` 对象，字段名与模板绑定一致。
3. REST PUT 修改 ACF 字段后，前台对应 heading、paragraph、image 或 button 更新。
4. 图片字段返回 URL，前台 `<img src>` 正确；alt 能同步。
5. customTemplates 只出现在指定 CPT 的模板选择器中。
6. 数据库中没有正式模板被后台编辑器覆盖；模板真源仍在主题文件。
7. ACF 后台表单可以修改字段，用户不需要直接编辑区块 JSON。
8. 空字段有安全降级，模板不出现布局塌陷或空标题。
9. 桌面端与 390px 移动端均通过视觉评分卡。
10. 工具链在 ACF 缺失或绑定源缺失时报出明确错误。

## 8. 风险与约束

1. **版本漂移**：ACF 绑定 UI 和 datastore 行为随版本演进，安装后必须探测，不假设文档版本永远一致。
2. **复杂字段**：Repeater、Gallery、Group、Relationship 不能直接当作简单绑定值；应映射为多个简单字段或交给自定义模板渲染。
3. **图片语义**：image field 要明确返回 URL；附件 ID 返回值不能直接填入 `core/image` 的 `url` 绑定。
4. **安全边界**：CTA URL 必须使用 ACF URL 字段和 REST 校验，避免模板输出不受控链接。
5. **DB 覆盖**：后台模板编辑器保存会覆盖主题模板。AI 修改模板时必须先读取主题文件，再部署到运行站，不把数据库模板当真源。
6. **设计质量**：绑定只解决数据复用，不自动解决好看。模板必须继承设计 token、pattern 和响应式规则。

## 10. wpagent 参考项目对标（2026-09-19）

研究样本：`/Users/Zhuanz1/MyProject/wpagent/wordpress-projects/`（astra-child / hello-elementor-child / html / prompts / ssh-deploy）。

### 10.1 对方架构本质

- **管线**：`需求 → HTML 预览（Tailwind CDN + Alpine.js CDN，preview-[name]-v{n}.html）→ WordPress 自定义页面模板（page-[name]-v{n}.php）+ ACF 本地字段组（acf-[name]-fields-v{n}.php）→ SSH/rsync/expect 单文件与批量同步 → 后台选模板填字段`。
- **数据层**：ACF local field group 按模板文件逐页组织，`location: page_template == tailwind-templates/page-xxx.php`；图片 `return_format: array`；常用 Tab 分组、默认值、`acf/load_field` 全局默认值过滤器。
- **渲染层**：每个页面模板是完整 HTML 文档壳（`wp_head()` + `wp_footer()`），Tailwind/Alpine 走 CDN；表单统一 Fluent Forms 短代码；`get_field() ?: '默认值'` 防空值。
- **设计系统**：`html/WEBSITE-DESIGN-SYSTEM.md` 版本化维护（色彩三方案、组件 HTML 片段、按钮/卡片/动画/断点、避免事项、版本历史），作为 HTML 生成的前置上下文。
- **部署层**：Python + expect/sshpass 的 `sync-single / sync-folder / deploy-rsync / deploy-full / backup-manager` 五件套，单文件 2-3 秒热更，完整发布自动备份。
- **前端可视化编辑**：Astra child 内置 `modules/visual-editor`（contenteditable + AJAX `update_field` + nonce），以及 `acf-ajax-handler.php` 直接写 ACF 字段。

### 10.2 关键启发（已采纳）

1. **自由 HTML 模板的价值被实战验证**：对方完全放弃区块限制，靠「完整文档壳 PHP 模板 + ACF」做出好看的 B2B 页面。这与本方案 D 模式结论一致；差别是我们保留 Block Theme 身份（`templates/index.html` + template parts），对方是 classic child theme。
2. **必须补「HTML 预览中间层」**：对方每个页面先产出可独立打开的静态 HTML（含 `data-field` 标记），确认视觉效果后再转模板。这解决"AI 直出 WordPress 后才发现丑"的问题。我们的管线在模板生成前应插入同样的 `design/preview-[page]-v{n}.html` 阶段，并要求 `data-field`/`data-bind` 标记与 ACF 字段一一对应。
3. **字段组跟随模板、按页面分文件**：`acf-*.php` 与 `page-*.php` 成对出现、命名对齐、location 绑定页面模板。比单一全局字段组更可控，值得作为 C 模式（页面级 ACF 组）标准写入管线；产品/案例等 CPT 字段组仍走插件统一注册（octopus-site 模式）。
4. **设计系统必须版本化并带更新记录**：对方把设计规范当活文档（含避免事项、用户反馈驱动更新）。我们的 `references/design.md` 应升级为同样格式：组件 HTML 片段 + token + 避免清单 + 版本历史。
5. **部署要分层**：单文件热更 / 文件夹同步 / 全量备份三种粒度。我们目前只有 rsync 全量，可补充"单模板快速同步 + 备份"脚本约定。
6. **表单交给专业插件**：Fluent Forms 短代码替换手写表单，避免 AI 手搓表单处理逻辑。我们可在 Skill 推荐层加入 Fluent Forms（询盘表单场景）。
7. **前端可视化编辑**：对方自研 AJAX `update_field` 编辑器证明"自由 HTML 模板不等于后台不可视编辑"。D 模式的后台体验可由 ACF 字段表单承担，暂不引入自研前端编辑器（复杂度高、重复 ACF 能力）。

### 10.3 对方短板（我们不跟随）

- Tailwind CDN + Alpine CDN 直接上生产：运行时编译、体积与闪屏问题；我们坚持构建期 CSS（主题 `style.css` + design token）。
- classic child theme + Elementor/Hello 父主题：编辑器锁定在第三方生态；我们保持原生 Block Theme + 模板层级。
- 无 REST 化内容管道（靠 SSH 同步 + 后台手填）；我们保留 REST 读写 `acf` 对象的 Codex 管线。
- 图片 `return_format: array` 与 REST 写入不兼容（要 ID）；我们统一 `url` 并已实测 REST 写入需传附件 ID、渲染层自动转 URL。
- 字段组靠代码文件但无 `show_in_rest`/`allow_in_bindings` 意识；我们全部字段开启 REST 与绑定。

## 11. 全站重构补充实测（2026-09-19 晚）

1. **站点首页模板特殊性**：`get_front_page_template()` 只查 `front-page.php`，完全忽略 `_wp_page_template` 自定义模板设置（REST 写入返回成功但前台不生效）。且 `templates/front-page.html` 区块模板会压过 PHP。因此首页自由模板的正确形态是：主题根目录 `front-page.php`（一行 `require page-home-v1.php` 委托）+ 删除 `templates/front-page.html`。
2. **全站模板覆盖现状**（D 模式已成主体）：首页 `front-page.php`→`page-home-v1.php`（hero/stats ACF + 分类展示/精选机器/案例实查）、`archive-oct_product.php`、`taxonomy-oct_product_category.php`、`single-oct_product.php`、`single-oct_case.php`、`page-cases-v1.php`、`page-contact-v1.php`、`page-landing-v1.php`（9 个次级页统一：暗 hero + 正文 + CTA 带，`hide_cta` 开关）。区块模板仅剩 `product-dynamic.html`（B 模式备选）、`index/page/single/search/404`。
3. **首页 ACF 字段组**：hero 文案/图/CTA + 4 组 stat；分类展示、精选机器、案例 teaser 全部实时查询，不需要字段。
4. **PHP 语法教训**：`foreach ( $arr as array( $a, $b ) )` 非法（要用 `[$a, $b]`）；lab 无 php -l，parse error 只能靠前台 500 + debug.log 定位。
