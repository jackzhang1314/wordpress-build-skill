## 1. 方案定位

这套方案不是生成一个可安装主题，也不是用 Elementor / Divi / WPBakery 一类页面构建器，而是复用 WordPress 原生能力，自动产出用户可以继续维护的站点：

```text
已有 Block Theme
      +
原生 Gutenberg Blocks
      +
Custom Post Types（自定义内容类型）
      +
ACF / WordPress meta 字段
      +
原生 Query Loop / Block Bindings / Block Templates
      +
REST API 计划执行 / 浏览器验收
```

核心目标：

- 页面在 WordPress 原生编辑器中可继续编辑；
- 数据进入 CPT/字段，而不是散落在硬编码 HTML；
- 样式尽量沿用已有 Block Theme；
- API 写入后必须做匿名前台验收；
- 长流程可恢复、可审计、不会因为中断就盲目重写。

## 3. 关键执行原则

### 3.1 先发现，再写入

每次任务先执行 `doctor`，读取实际站点状态：

- WordPress REST root；
- 账号权限；
- active theme 是否为 Block Theme；
- 已注册 block types；
- 页面 schema 和可用 template；
- template parts；
- CPT / ACF / meta schema；
- 站点标题、描述和首页设置。

能力未知时按 unknown 处理，不自动推定成功。

### 3.2 页面使用受控区块 AST

页面不直接生成任意 HTML，而是先描述受限节点：

| 节点 | WordPress 输出 |
| --- | --- |
| `section` | `core/group` |
| `heading` | `core/heading` |
| `paragraph` | `core/paragraph` |
| `columns` | `core/columns` + `core/column` |
| `image` | `core/image` |
| `button` | `core/buttons` + `core/button` |
| `table` | `core/table` |
| `faq` | `core/details` + `core/paragraph` |
| `meta` | `core/paragraph` + `core/post-meta` binding |
| `catalog` | `core/query` / Query Loop |

限制：

- 不输出 arbitrary HTML；
- 不使用第三方 page builder 短代码；
- 区块必须真实注册；
- 内部链接必须能解析为真实页面；
- 媒体必须先上传并拿到真实 `mediaId`；
- 样式限制在安全属性内：背景、文字色、padding、radius、列宽。

### 3.3 计划、应用、回执三层分离

典型链路：

```text
site-plan.json
   ↓ build --plan
创建草稿
   ↓ 获取真实 page ID
解析 page:key 内链
   ↓ 保存回执
浏览器预览
   ↓ page-edit-plan / apply
正式改稿
   ↓ build --publish
发布并设置首页
```

任务目录保存：

- 原始计划 hash；
- 连接 identity；
- 每个页面状态；
- API 响应；
- readback 结果；
- 版本指纹；
- 媒体 hash；
- 操作日志。

因此中断后可以继续，不重复 POST；远端内容被人改过时会拒绝旧计划覆盖。

### 3.4 内容模型优先于硬编码内容

产品、案例、项目等业务内容进入 CPT，而不是塞进一个静态页面。

```text
oct_product
├── title
├── editor
├── excerpt
├── featured image
├── meta / ACF 字段
└── taxonomy（可选）
```

前台目录使用原生 Query Loop：

```json
{
  "type": "catalog",
  "postType": "oct_product",
  "perPage": 9
}
```

字段展示使用原生 Block Bindings：

```json
{
  "type": "meta",
  "key": "oct_lead_time",
  "fallback": "Lead time pending"
}
```

### 3.5 ACF 不是无条件可用

ACF 字段必须满足：

- field group 开放 REST；
- WordPress OPTIONS schema 暴露字段；
- 字段不是 readonly；
- 类型可安全转换；
- 不和 meta 同名重复写。

当前已验证文本字段。复杂 ACF 图片、repeater、relationship、group 字段需要单独适配，不能因 ACF 存在就承诺可用。

### 3.6 导航和模板做精确替换

导航不重写主题，而是：

1. `template-parts` 读取真实 header/footer；
2. 找到唯一匹配的原生 `core/navigation` fragment；
3. 生成前后稿；
4. 校验依赖版本；
5. 精确替换；
6. 回读确认。

CPT 详情页如果默认继承文章模板，可以创建专用 block template：

```text
single-oct_product
```

它保留真实 header/footer，只替换详情区。不能把该适配器误用于普通 post/page hierarchy。

### 3.7 发布前必须浏览器验收

API 成功只代表数据写入成功。发布前至少检查：

- 原生编辑器能识别所有 block；
- 单一 H1；
- 桌面和 390px 无横向溢出；
- 图片实际加载且 alt 正确；
- 按钮链接无占位符；
- 手机菜单可打开、关闭；
- 表格或列布局在窄屏可读；
- 匿名前台与管理端预览分开看。

发布后还要复查真实 permalink、首页、导航、产品详情和图片。

## 6. 当前能力边界

### 可以承诺的能力

- Block Theme 下生成受控原生页面；
- 页面草稿、预览、发布、首页设置；
- 真实媒体上传与引用；
- 已公开 CPT 的发现和内容创建；
- ACF / meta 文本字段更新；
- CSV 草稿批量导入；
- 原生 Query Loop；
- 简单原生导航精确替换；
- CPT 专用 block template；
- 任务目录恢复和操作审计。

### 不能自动承诺的能力

- 经典主题深度适配；
- 任意 ACF 复杂字段；
- 任意第三方 CPT 插件；
- 表单创建后的邮件送达；
- SEO 插件全版本兼容；
- WooCommerce 完整产品体系；
- 服务器、DNS、SSL、域名购买；
- 性能优化结论；
- 没有用户素材和授权时的真实企业发布。

## 7. 下一步建议

1. 给 `catalog` 增加受控 taxonomy / term / search 过滤，避免同类旧内容混入；
2. 抽象一套 B2B 外贸页面 pattern 库：Home、Products、Factory、Case、FAQ、Contact；
3. 扩展 CPT 模板验收矩阵，覆盖更多 Block Theme；
4. 增加 ACF 图片 / relationship / repeater 的安全适配研究；
5. 建立真实 HTTPS WordPress 站验收脚本；
6. 增加发布前 Lighthouse / SEO 基础检查；
7. 对表单插件和邮件送达做独立流程，不把“表单存在”当成“询盘能收到”。
