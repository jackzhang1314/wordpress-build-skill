# 新项目研究与实施路线

> 历史资料：本文件保留当时方案与验收，不是当前执行规范。当前仅支持新站，入口见 [系统架构](ARCHITECTURE.md) 与 [新站总编排](../.agents/skills/wordpress-builder/SKILL.md)。

这是后续建议，尚未在本资料仓库实施。先读会话决策和真实失败记录，再选择宿主与实现方式。

## 第一阶段：建立一个可信的最小测试闭环

使用隔离 WordPress 和明确标注的示例企业资料。先实现并验证：连接状态 → 读取一个已有页面 → 修改一个原生段落为草稿 → API回读 → 浏览器预览 → 用户授权后发布 → 记录ID/URL/状态。之后再扩成四页和整站任务。

测试启动必须校验模型配置、连接器状态、实际加载的构建身份、当前工具清单、侧栏/任务RPC及一个只读调用。发现测试控制超时先停止诊断，不继续创建长模型任务。只展示hasKey等状态，不记录实际密钥。

## 第二阶段：适配 Skill 与连接器

- 先接 `wordpress-block-pages`，实现它引用的工具和任务文件接口；不要一开始加载所有SEO和地图工具。
- 保留最新完整正文回执、固定文件版本、明确的截断标记和来源。
- 把每页的ID、状态、modifiedGmt、写入回执、预览URL、未完成项持久化；恢复后从下一动作继续。
- 审批与执行分离，未知写不重发；客户端变化检查的并发窗口必须明确。
- 检查来源Skill的工具名与新宿主一致，不用“已安装Skill”代替连接器可用性测试。

## 第三阶段：四页建站与主题适配

复用用户现有主题，测试至少一个区块主题，并明确经典主题支持范围。完成首页、产品页、关于、联系页，检查标题层级、原生块有效性、素材、链接和移动端布局，再发布和设置首页。简单导航使用受控计划，不先做任意全站模板编辑。

页面编辑与发布要分开建模：原实现更新page要求提交blocks，单纯改变状态也可能需要重建正文。新项目应研究是否引入独立的受控“改变状态”接口，减少为发布而重新序列化已验收内容；这是候选改进，不是当前已实现工具。

## 第四阶段：结构化内容与运营

按用户站点需要增加CPT/ACF、CSV产品、媒体、询盘表单，再接SEO内容工作室与DataForSEO。每项分别验收真实字段、模板展示、实际发布和表单送达，不能用静态演示代替。

## 需要重点补研究的事项

| 问题 | 研究/验收方法 |
| --- | --- |
| 长任务重复检查 | 比较每轮上下文、压缩前后保留的任务目标/完成项/下一动作，统计重复工具与真实写入推进 |
| 工具列表过大 | 记录每场景实际工具数量、schema体积、模型输入与压缩次数；按需分组效果需真实模型验证 |
| 浏览器控制不稳定 | 区分测试CDP、侧栏生命周期、产品RPC、实际网页动作和服务端响应，不混为一个错误 |
| WordPress安装兼容 | 官方REST根、子目录、反向代理、认证、权限不足和不同托管方式 |
| 页面内容保留 | 未支持区块、用户人工修改、修订、发布前后比较；避免整页重建丢失内容 |
| ACF前台展示 | 字段写入后实际页面变化、动态绑定方式、现有模板兼容 |
| 表单送达 | 专用测试收件箱、通知设置、垃圾邮件/SMTP环境；创建表单不等于送达 |
| 对外发布仓库 | 移除环境私有信息、按文件核对许可证/上游来源、补安装与能力需求说明；本次没有执行公开发布 |

建议以“任务正确完成率、重复写次数、恢复准确率、重复读取、耗时和模型费用”评估，不以Skill数量或代码行数代替效果。不要先把之前整套浏览器扩展复制成新应用；优先复用已验证的业务工具，宿主接口单独定义。

## 开新会话时可使用的任务说明

> 请先阅读 README.md 和 docs/01 至 04。当前目标是用户仅用浏览器 AI Agent 完成标准 WordPress 外贸网站建设与运营；采用原生区块和共享连接器，沿用现有主题，不捆绑主题，不默认依赖 Codex。这里是研究资料和Skill快照，不是完整运行应用。请先核对最新官方能力和来源代码，再给出独立项目的宿主、Skill、连接器与验证方案。先做一个页面的真实模型闭环，解决重复读取与恢复问题后再扩四页。旧主题实验和过往局部测试不能当成当前整体验收通过。
