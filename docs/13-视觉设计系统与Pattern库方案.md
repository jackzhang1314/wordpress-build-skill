# 视觉设计系统与 Pattern 库方案

研究日期：2026-09-19（Asia/Shanghai / CST）。

触发原因：延续《12-WordPress-AI建站生态研究》的结论，把 AI 建站方案缺失的设计层落成可执行规格。本文展开 12 层方案中的第 1-9 层；第 10-12 层只在路线图中作为后续方向提及。

来源类型说明：WordPress 机制以官方机制与公开技术文档为依据；设计、文案、转化、SEO、性能和 QA 规则以公开社区分析、竞品公开资料、内部样板站验收观察和 frontend-design 方法论综合而成。本文不虚构具体 URL。

## 总体结论

视觉层必须与 CMS 层同等级交付。核心做法是：

1. theme.json 是设计 token 的唯一真源。
2. 命名 pattern 是可复用业务组件，不散装堆 HTML。
3. 每个 CPT 和站点状态都有对应模板。
4. 文案、媒体、转化、SEO 和性能都进入验收规则。
5. 发布前必须通过 24 分制视觉评分卡，并以 Playwright 截图、CWV 实测和链接检查作为证据。

本文的规格按层描述，但实施时层 1、2、6 必须优先落地，否则后续页面仍会回到“数据正确但视觉平庸”的状态。

## 层 1：设计 token

### 1.1 唯一真源

`theme.json` 是设计 token 的唯一真源。主题内的 PHP、pattern、模板和组件文档不得另建第二套颜色、字号、间距、圆角或阴影命名体系。

token 分为五类：

| Token 家族 | 数量 | 必须覆盖 |
| --- | ---: | --- |
| 色板 | 8 档 | 页面底色、表面色、主文字、次级文字、主行动/信号色、辅助强调色、浅分区/中性色、分隔线 |
| 字号 | 6 档 | Display/H1、H2、H3 或卡片标题、正文、辅助说明、技术标签/小字 |
| 间距 | 8 档 | xs、sm、md、lg、xl、2xl、3xl、section，形成稳定节奏 |
| 圆角 | 4 档 | sharp、control、card、pill 或等效命名 |
| 阴影/行高 | custom token | 2-3 档阴影与标题/正文/紧凑/表格行高 |

色板建议命名语义化，不使用 `blue-500`、`gray-100` 这类容易脱离角色的名称。示例命名：

```text
base
surface
ink
muted
signal
secondary-signal
neutral
line
```

字号建议命名：

```text
display-xl
heading-lg
heading-md
body-lg
body-sm
technical-sm
```

### 1.2 主题与 CSS 的分工

`theme.json` 负责：

- 色板、渐变禁用或受控白名单。
- 字号、字体族、字重、行高。
- padding、margin、contentSize、wideSize 和 spacing sizes。
- 圆角与阴影 custom token。
- 默认排版、区块默认样式和可选调色板约束。

`style.css` 只负责：

- 消费 `var:preset|...` 或对应 CSS 自定义属性。
- 处理 theme.json 难以表达的结构性伪元素、focus 状态、打印样式或少量组件组合逻辑。
- 不得重新定义第二套业务 token。

### 1.3 禁止裸值

`style.css` 禁止裸色值和裸 px：

- 不允许 `#hex`、`rgb()`、`hsl()`、`oklch()` 等裸颜色。
- 不允许随意写 `padding: 13px`、`font-size: 17px`、`border-radius: 6px`。
- 布局尺寸优先使用 theme.json spacing、百分比、`rem`、`clamp()` 或语义变量。
- `rem` 的基础换算、断点和容器最大宽度必须在主题内集中声明，不在各组件中各自硬编码。

如确需引入新值，先加入 theme.json，再在样式中引用。

### 1.4 Style Variations

主题应预留至少一个默认风格和一个可切换风格，例如：

```text
styles/
  industrial-light.json
  industrial-dark.json
```

Style Variation 只覆盖 token 值和必要全局样式，不复制模板结构，也不定义另一套 pattern。这样可保证同一 pattern 在不同风格下仍保持层级一致。

### 1.5 验收

层 1 通过标准：

1. theme.json 含 8 档色板、6 档字号、8 档间距、圆角、阴影和行高 token。
2. style.css 无裸色值；除非集中声明的布局基础值，无散落裸 px。
3. 编辑器与前台使用同一批预设变量。
4. 至少一个 Style Variation 可切换且不破坏模板结构。
5. 对比度满足正文和交互文本的可读性要求。

## 层 2：Pattern 库

### 2.1 注册机制

所有核心区块组合通过 WordPress 官方 `register_block_pattern()` 注册，不做复制粘贴式散装 HTML。建议统一前缀，例如 `wbs/`，并建立独立 pattern category，如 `B2B Sections`。

推荐目录：

```text
patterns/
  hero.php
  product-grid.php
  spec-table.php
  process.php
  faq.php
  cta.php
  trust-bar.php
  case-grid.php
```

每个文件只输出合法原生区块 markup，并由 `register_block_pattern()` 提供稳定名称、标题、描述和分类。

### 2.2 首批 10-15 个命名 pattern

| Pattern | 用途 | 关键约束 |
| --- | --- | --- |
| hero | 首屏价值主张、支撑信息、主/次 CTA | 一个 H1；主 CTA 明确；图片有场景；不能堆四个以上卖点 |
| product-grid | 产品/方案目录 | Query Loop 或受控区块卡；固定图片比例；标题层级一致；分页可用 |
| spec-table | 技术参数表 | 表头、字段名、单位、备注层级分明；移动端不横向失控 |
| process | 询盘、交付、安装或服务流程 | 3-5 步；编号清晰；每步有动词和结果 |
| faq | 常见问题 | 问题来自真实业务；答案可验证；可配合 details/accordion 类原生结构 |
| cta | 询盘或下一步行动 | 一个主行动；说明减少决策阻力；不使用空洞口号 |
| trust-bar | 证书、工厂、交付、服务或合作证据 | 每项可溯源；不使用无来源认证图；数量克制 |
| case-grid | 案例/应用目录 | 统一封面比例；显示行业、对象和结果；不写成广告文案 |
| solution-split | 场景/解决方案左文右图或左图右文 | 图文关系明确；避免每个 section 相同镜像 |
| stats | 产能、交付、服务范围等量化证据 | 数字有口径；不超过 3-4 项；移动端可读 |
| industry-list | 行业/应用入口 | 每项链接到真实 term 或页面；图标或图片角色统一 |
| comparison | 型号/方案选择 | 避免贬损竞品；差异字段可核实；CTA 明确 |
| contact-panel | 联系与 RFQ 入口 | 最小字段；隐私提示；错误态可访问 |
| quote/testimonial | 客户声音 | 有客户、行业、时间或可验证背景；不虚构姓名与 logo |
| footer-nav | 结构化 footer 导航 | 分组明确；覆盖产品、应用、支持、公司与合规信息 |

实际站点可按行业选择 10 个以上；通用库应稳定保留 hero、product-grid、spec-table、process、faq、cta、trust-bar、case-grid。

### 2.3 Token 引用规则

pattern 内只允许引用 theme.json 预设，不允许内联裸样式。颜色、字号、间距、圆角、阴影按如下形式表达：

```text
var:preset|color|base
var:preset|color|signal
var:preset|font-size|display-xl
var:preset|spacing|lg
var:preset|custom|radius-card
```

禁止：

```text
style="color:#333"
style="padding:22px 31px"
style="font-size:18.5px"
```

pattern 可以定义布局属性，例如 `align`、`layout`、列数、最小高度和响应式堆叠，但视觉值必须来自 token。

### 2.4 内容槽位与可替换性

每个 pattern 必须能在编辑器中替换内容：

1. 标题、导语、正文和 CTA 是普通 heading/paragraph/button 区块。
2. 图片引用 media library，不内嵌 base64。
3. 列表项可增删，不依赖隐藏注释。
4. 不使用只能通过改代码修改的魔法文本。
5. pattern 名称表达业务结构，不表达某次营销活动。

### 2.5 验收

层 2 通过标准：

1. 至少注册 10 个命名 pattern，能在编辑器分类中找到。
2. 每个 pattern 在默认与 Style Variation 下均渲染正常。
3. pattern 内无裸色值/裸 px，只有 token 引用。
4. 每个核心 pattern 有桌面和移动截图。
5. 替换标题、图片、列表项和 CTA 后不破坏布局。

## 层 3：模板补全

### 3.1 必补模板

当前路线必须补齐以下模板：

```text
templates/archive-oct_product.html
templates/taxonomy.html
templates/search.html
templates/404.html
```

它们分别解决产品目录、分类/标签、搜索结果和站点死路四类常见页面，避免这些页面回落到默认 blog 样式。

### 3.2 archive-oct_product.html

结构要求：

1. 顶部使用 hero-lite 或页面标题 pattern，说明产品目录范围。
2. 产品项显示 featured image、产品名、核心规格或行业标签、一个简短价值点。
3. 图片统一产品比例 4:3，卡片内标题层级一致。
4. 使用 Query Loop 或等价原生查询结构，支持分页。
5. 无结果时提供行业入口、搜索框或询盘入口。
6. 不在目录页塞入完整参数表；复杂参数留给详情页。

### 3.3 taxonomy.html

结构要求：

1. 顶部显示 term 名称与简介，说明该行业/应用/分类覆盖什么产品或场景。
2. 列出该 term 下的产品、案例或相关内容。
3. 提供相邻 term 或父级 term 导航，避免用户进入孤岛页面。
4. term 无内容时显示真实空态，并给出联系、热门产品或全目录入口。
5. term 页面标题、面包屑和 canonical 保持唯一。

### 3.4 search.html

结构要求：

1. 显示用户查询词与结果数量。
2. 结果卡显示标题、类型、摘要或关键图片，区分产品、案例、页面与文章。
3. 空结果提供热门产品、行业目录、联系入口和修正关键词建议。
4. 搜索结果页设置 noindex。
5. 不把搜索词直接注入未转义文本，避免反射类风险。

### 3.5 404.html

结构要求：

1. 明确说明页面不存在，不指责用户。
2. 提供首页、产品目录、案例、联系方式和搜索框。
3. 可列出 3-6 个高频入口。
4. 保持主品牌样式与 header/footer，不使用裸默认主题。
5. 不产生额外重定向循环。

### 3.6 验收

层 3 通过标准：

1. 四个模板在 Block Theme 中生效。
2. 每个模板在桌面 1440px、平板 820px、手机 390px 无横向溢出。
3. 有结果与无结果状态均有截图。
4. 分页、term、搜索和 404 URL 检查通过。
5. 页面均使用站点设计 token，不回落默认 blog 视觉。

## 层 4：反 AI 味文案

### 4.1 行业语调 profile

面向 B2B 工业与产品型站点，默认语调是“工程化、可验证、克制、可执行”：

1. 说产品做什么，不说“改变世界”。
2. 说参数、工况、产能、服务范围，不堆形容词。
3. 说下一步动作，例如 Request a quote、Download spec、Book a factory visit。
4. 不冒充客户成就，不使用无法核实的认证。
5. 允许有品牌性格，但技术页面优先准确性。

可按行业微调：

| 行业 | 语调重点 | 应出现的信息 |
| --- | --- | --- |
| 机械设备 | 精度、负载、工况、交付 | 型号、产能、材质、控制系统、售后 |
| 建材/工程 | 规格、施工场景、认证 | 尺寸、强度、项目类型、合规 |
| 制造/OEM | 定制、批量、质量、交期 | MOQ、图纸能力、检测、包装 |
| 科技/工业软件 | 场景、集成、安全、可观测 | 数据接口、权限、部署、支持 |

### 4.2 首屏公式

首屏标题使用：

```text
具体产品/能力 + 数字/规格/场景 + 动词或结果
```

可用结构：

1. “产品类型 + 处理/覆盖/承载 + 数字 + 应用场景”
2. “产品线 + 核心规格 + 动词 + 目标结果”
3. “行业场景 + 产品能力 + 询盘/交付动作”

首屏副标题必须回答：

1. 这是什么。
2. 适合谁。
3. 关键差异或规格。
4. 下一步做什么。

禁止首屏只有品牌名和一句空洞 slogan。

### 4.3 禁用词清单

默认禁用或必须改写为具体证据的词包括：

```text
enterprise-grade
cutting-edge
seamless
world-class
best-in-class
revolutionary
game-changing
synergy
one-stop solution
state-of-the-art
unparalleled
next-generation
empower
robust solution
high quality
```

规则：

1. 这些词不能单独作为卖点。
2. 如必须提及，应跟随之认证、参数、流程、案例或服务范围。
3. 禁止把“高质量”当作标题；应写检测流程、公差、材料、交付或质保。
4. 竞争对比不得使用无依据贬损。

### 4.4 段落与结构规则

1. 首段不超过三句，先给事实再给解释。
2. 每个产品页至少有：适用场景、关键规格、差异点、服务/交付、下一步动作。
3. 案例采用“客户场景—约束—方案—结果”结构，可匿名但不得虚构。
4. FAQ 问题应来自真实询盘、合规要求、安装、售后或采购流程。
5. 英文站避免中式直译；技术术语优先行业通用表达。

### 4.5 验收

层 4 通过标准：

1. 首屏标题符合公式且至少有一个具体事实。
2. 禁用词清单检查无未处理命中。
3. 每个关键声明有规格、案例、认证或流程支撑。
4. 无虚构客户、logo、证书和数量。
5. 英文文案符合行业语调 profile。

## 层 5：媒体管线

### 5.1 授权规则

媒体必须满足以下任一条件并记录来源：

1. 客户或项目方拥有版权并书面授权。
2. 使用明确 CC0 或可商用授权的素材。
3. 使用原创生成图、原创渲染图或原创示意图。

禁止：

1. 未经授权抓取竞品或搜索引擎图片。
2. 使用“看起来像免费”但授权不明的素材。
3. 使用他人 logo、客户案例、人员照片作为信任证明。

媒体库中至少记录来源类型、授权类型、拍摄/生成日期或项目归属。必要时使用自定义字段或媒体描述保存记录。

### 5.2 裁切与比例

默认比例：

| 媒体类型 | 比例 | 用途 |
| --- | ---: | --- |
| 产品图 | 4:3 | 产品目录卡、产品详情主图、参数旁图 |
| 场景图 | 16:10 | hero、行业应用、案例封面 |
| 团队/工厂 | 4:3 或 16:10 | 保持同组一致，不混用任意比例 |
| 图标/标记 | 1:1 | trust bar、服务项、industry list |

同一列表内禁止混用不同裁切比例。上传时预裁切，前端不依赖 CSS 强行拉伸。

### 5.3 格式与尺寸

1. 照片导出 WebP，必要时提供合理 fallback。
2. 产品主图按卡片和详情两个尺寸生成，避免桌面加载移动图。
3. 使用 `srcset`/`sizes` 或 WordPress 自动尺寸。
4. 压缩后无明显色带、结构线丢失或文字模糊。
5. 图标优先 SVG，不用大 PNG 模拟图标。

### 5.4 alt 与可访问性

alt 使用“对象 + 动作/场景 + 关键属性”的描述式规则：

- 好例子：`Compact loader clearing snow from a warehouse yard`
- 差例子：`image`、`product`、`machine1`

补充规则：

1. 装饰性图形使用空 alt 或交给 CSS/background，不用重复无意义文字。
2. 含关键文字的图片应在正文或 aria 文本中提供等价信息。
3. 文件名使用英文短横线，不含临时编号乱码。
4. 不同语言站点提供本地化 alt。

### 5.5 首屏与加载优先级

1. 首屏主图使用 `fetchpriority="high"`，且每屏只允许一个高优先级主图。
2. 非首屏图片 lazy load。
3. hero 不叠加阻塞脚本。
4. 首屏图片尺寸与实际显示区域接近，避免加载超大图。
5. 图片容器预设比例或最小尺寸，避免 CLS。

### 5.6 验收

层 5 通过标准：

1. 每张媒体可追溯到授权来源。
2. 列表比例统一，无拉伸或明显裁切主体。
3. WebP、尺寸、alt 和 lazy/high priority 规则生效。
4. 首屏图片不导致 LCP 失控或 CLS。
5. 移动端图片清晰度可接受，无文字不可读。

## 层 6：视觉 QA 评分卡

### 6.1 评分原则

采用 6 个维度、每维 0-4 分、总分 24 分制。评分对象是实际渲染页面截图，不是设计稿或代码意图。

每次评分必须写：

1. 页面 URL。
2. 视口：桌面 1440px、平板 820px、手机 390px。
3. 扣分原因。
4. 修复动作：token、pattern、模板或文案。
5. 下一轮截图路径。

### 6.2 六个维度

| 维度 | 0 分表现 | 2 分表现 | 4 分标准 |
| --- | --- | --- | --- |
| 层级 | 用户无法判断先看哪里 | 主标题清楚，但 section 主次不清 | 首屏、章节、卡片和 CTA 有清晰阅读顺序 |
| 排版 | 字号/行高混乱 | 有字号层级但密度不稳 | 字号、行高、字重、标签和表格形成稳定节奏 |
| 色彩 | 颜色多且无角色 | 主色可用但强调混乱 | 底色、表面、文字、信号色和分隔线职责明确 |
| 布局 | 有横向溢出或元素碰撞 | 基本对齐但间距随机 | 栅格稳定、间距节奏一致、三视口无溢出 |
| 细节 | 按钮态/表格/图片低质 | 主要组件可用但状态不完整 | focus/hover/empty/error/table/media 都完成 |
| 反模板感 | 看起来是通用 SaaS 模板 | 有差异化但风格不连续 | 有连续签名元素，且服务于业务与可读性 |

### 6.3 发布门槛与迭代限制

1. **≥20/24 可发布。**
2. 任一维度 0 分不可发布，即使总分达到 20。
3. 桌面与手机分别评分；最终分数取较低者，不能只看桌面。
4. 每个页面最多 3 轮迭代。
5. 第 3 轮仍低于 20 分时，停止继续调样式，回到信息架构、内容或设计方向层复盘。

### 6.4 必查项

评分卡之外还必须断言：

1. 页面只有单一 H1。
2. 桌面 1440px 与手机 390px 无横向溢出。
3. 主 CTA 可见且可聚焦。
4. 图片有 alt，容器无异常拉伸。
5. 交互文本对比度可读。
6. header/footer 与当前主题一致。
7. Playwright 截图、DOM 断言和链接检查证据保存。

## 层 7：B2B 转化层

### 7.1 sticky CTA

产品、行业、案例和联系相关页面应有持续可达的询盘入口。

要求：

1. 桌面可用 header CTA、右侧浮动面板或底部窄条，不遮挡正文核心区。
2. 移动端使用底部 sticky CTA，高度不超过一屏可承受范围。
3. 主文案使用具体动作，如 Request a quote、Get specifications、Book a factory visit。
4. 不使用自动弹窗、自动播放声音或强制注册。
5. 用户滚动到核心内容后 sticky CTA 仍可见；关闭状态可恢复。

### 7.2 RFQ 最小字段

RFQ 表单只收集完成初步回复所需信息，默认字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| Product / model | 是 | 可预填来源产品 |
| Quantity / timeline | 是 | 帮助判断采购阶段 |
| Contact name | 是 | 后续回复对象 |
| Company | 是 | B2B 合格线索基础 |
| Email | 是 | 主回复渠道 |
| Phone / WhatsApp | 条件 | 允许留空或作为备选 |
| Country / region | 是 | 判断市场、合规和服务范围 |
| Requirements | 是 | 工况、规格、用途、约束 |
| Attachment | 否 | 图纸、清单或参考文件 |

补充规则：

1. 首次提交不超过 8-10 个输入项。
2. 明示隐私用途与联系目的。
3. 错误提示写到字段附近，不能只靠颜色区分。
4. 提交成功页给出下一步时间和可选资料。
5. 不要求注册账号才能发询盘。

### 7.3 信任信号位

信任信号必须有来源，不使用虚构 logo、假证书或不可验证口号。

推荐位置：

1. hero 下方：服务范围、交付能力、核心认证或服务市场。
2. 产品详情：质保、检测、包装、交期、售后。
3. 案例页：行业、地区、项目类型、使用结果。
4. contact/RFQ：响应时间、支持语言、负责人角色、工厂/服务能力。

可使用的信号类型：

- 真实认证与标准。
- 工厂、设备、检测流程照片。
- 出口/服务国家或区域。
- 交付流程和售后响应。
- 可核实的客户类型或项目类型。

## 层 8：SEO + 多语言

### 8.1 Schema 要求

至少实现三类结构化数据：

1. **Product**
   - 名称、图片、描述、品牌、SKU/型号。
   - 有明确售价时可提供 offers；报价制产品不得编造价格。
   - 产品规格可用受控属性表达，不把所有信息塞进 description。
2. **Organization**
   - 站点/公司名称、logo、URL、联系方式或联系入口。
   - 有真实社交或公开资料时再添加 sameAs。
3. **BreadcrumbList**
   - 首页、目录、分类、详情路径一致。
   - 与页面可见面包屑和 URL 层级不冲突。

Schema 与可见内容必须一致，不输出页面中不存在的价格、评分、库存或认证。

### 8.2 hreflang 与多语言

多语言站点要求：

1. 每个翻译版本有唯一 URL，不靠参数伪装成独立语言页。
2. hreflang 双向互指，并包含自引用。
3. 需要默认页时设置 `x-default`。
4. hreflang 与 canonical 不冲突。
5. 语言切换器保持当前内容路径，尽量跳到对应翻译，而不是一律回首页。
6. 翻译缺页时提供清晰状态或降级页，不用自动跳转吞掉用户路径。
7. slug、标题、meta description、alt 和 schema 文本本地化，不只翻译正文。

### 8.3 页面 SEO 结构

| 页面 | 标题结构 | 必须有 |
| --- | --- | --- |
| 首页 | 品牌 + 核心业务/市场 | 主导航、首屏价值、产品入口、信任信号、联系入口 |
| 产品目录 | Products + 行业/品类 + 品牌 | 产品卡、筛选或分组、分页、询盘入口 |
| 产品详情 | 型号/产品名 + 关键能力 | 图集、规格、场景、质保、RFQ、相关产品 |
| 行业页 | Industry/Application + 场景 | 行业简介、适用产品、案例、入口 |
| 案例 | 行业/对象 + 结果类型 | 背景、约束、方案、结果、相关产品 |
| 联系/RFQ | Contact/Request a quote + 品牌 | 表单、响应说明、联系信息、隐私提示 |

meta description 概括对象、能力和下一步动作，不复述标题。

## 层 9：性能

### 9.1 CWV 实测进入 QA 循环

视觉发布门槛必须叠加性能检查：

| 指标 | 目标 |
| --- | ---: |
| LCP | < 2.5s |
| CLS | < 0.1 |
| INP | < 200ms |
| FCP | 参考项，不做单独发布门槛 |
| TTFB | 参考主机与网络环境，用于排查 |

要求：

1. 首页、产品目录、产品详情、案例、联系页至少实测一次。
2. 桌面与移动均记录，移动结果作为主要门槛。
3. 每次重大 pattern 或首页改动后重测。
4. 不只看实验室分数，要结合资源清单和瓶颈。

### 9.2 字体本地托管

1. 字体文件本地托管，不依赖第三方公共 CDN 作为关键渲染资源。
2. 使用 WOFF2，按实际字重和字符集子集化。
3. display/body/technical 三个角色的字体族集中定义。
4. 首屏关键字体可 preload，但数量克制。
5. 提供 metric-compatible fallback，减少字体交换引起的 CLS。
6. 不为少量标题加载完整多字重全家桶。

### 9.3 无 jQuery 与第三方脚本约束

前台主题不加载 jQuery：

1. 菜单、accordion、轮播、表单增强优先使用原生 JavaScript。
2. 不为简单交互引入大型框架。
3. 必需脚本加 `defer` 或按需加载。
4. 第三方分析、客服、地图和广告脚本必须逐个审批。
5. 第三方资源不得阻塞首屏交互。
6. 移除主题内的重复 polyfill、重复字体和未用 CSS。

### 9.4 其他规则

1. CSS 按 Block Theme 正常加载，不做隐藏关键内容的伪优化。
2. 图片按层 5 规则处理。
3. 缓存策略由宿主配置，主题不自行做破坏性缓存逻辑。
4. HTTP 资源统一 HTTPS。
5. 控制台不得出现新增 JS 错误。

### 9.5 验收

层 9 通过标准：

1. 关键页面 CWV 达标并保存证据。
2. 前台无 jQuery 依赖。
3. 本地字体加载链路无第三方阻塞。
4. 首屏资源无重复字体/超大图。
5. 重大视觉迭代后性能未回退。

## 层 10-12：路线图

层 10-12 属于后续路线图：层 10 作为文案与版式内容扩展能力纳入下一阶段；层 11 用于对齐官方 Abilities API/MCP Adapter 生态；层 12 抽象为可复用的 `wp.mjs` 产品化 demo。

## P0-P3 实施顺序

### P0：先解决“能看、能维护、可验收”

包含层 1 + 层 2 + 层 6。

交付：

1. theme.json 完整 token 体系。
2. 至少 10 个命名 pattern。
3. 24 分制视觉评分卡和 Playwright 截图流程。

退出条件：

1. style.css 不再补丁式裸样式。
2. 核心页面可由 token + pattern 组合生成。
3. 评分 ≥20/24 才允许发布。

### P1：补齐站点结构与内容质量

包含层 3 + 层 4 + 层 10。

交付：

1. archive-oct_product、taxonomy、search、404 模板。
2. 行业语调 profile、首屏公式、禁用词检查。
3. 文案与版式内容扩展层。

退出条件：

1. 四类模板在关键视口稳定。
2. 首屏和关键页无空洞 slogan。
3. 禁用词与声明可验证性检查通过。

### P2：完成转化、合规与性能

包含层 7 + 层 8 + 层 9。

交付：

1. sticky CTA、RFQ 最小字段、信任信号。
2. Product/Organization/BreadcrumbList schema 与 hreflang。
3. CWV 实测、本地字体、无 jQuery。

退出条件：

1. B2B 询盘路径三步内可达。
2. Schema 与 hreflang 校验通过。
3. 移动端 LCP/CLS/INP 达标。

### P3：完善媒体与产品化

包含层 5 完善 + 层 11 生态对齐 + 层 12 产品化。

交付：

1. 媒体授权、裁切、WebP、alt 和首屏优先级全链路工具化。
2. Abilities API/MCP Adapter 能力契约对齐。
3. `wp.mjs` demo 抽象建站流程，使新站点可以复用同一管线。

退出条件：

1. 新站点无需重写核心样式与 QA 逻辑即可复用主题基座。
2. 建站动作能映射为稳定能力描述。
3. demo 输出包含内容、模板、token、pattern、截图与性能证据。

## 最终验收口径

一个站点只有同时满足以下条件，才视为完成视觉设计系统交付：

1. CMS 层：CPT/ACF/REST 数据可写入、可编辑、可查询。
2. 结构层：Block Theme、CPT 模板和命名 pattern 生效。
3. 设计层：theme.json token 唯一真源，style.css 无裸值补丁。
4. 内容层：首屏、参数、案例、FAQ 和 CTA 具体可验证。
5. 转化层：询盘入口、表单和信任信号完整。
6. 质量层：视觉评分 ≥20/24，三视口无横向溢出。
7. 技术层：SEO、hreflang、CWV、字体和脚本约束达标。
8. 证据层：截图、DOM 断言、链接检查、性能实测和验收记录可追溯。
